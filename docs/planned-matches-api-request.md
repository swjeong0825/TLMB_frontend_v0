# Backend Main request: planned matches

Implement the API described here in Backend Main. The frontend already supports local
drafts and an upload stub; no planned-match endpoints are called yet. Chat-to-Intent
is not involved. Backend implementation and deployment are separate from this frontend change.

## Purpose and permissions

A plan is a proposed matchup without scores. Anyone with a league link can upload
plans and read that league's shared list, without a host token. Keep records isolated
by league. Reuse the service's normal league existence checks and CORS configuration.

Do **not** resolve nicknames to player IDs, enforce roster membership or pair/rematch
rules, register players/pairs, create recorded matches, or change standings. Unknown
nicknames are valid even when `auto_register_players_on_match` is false. The frontend
shows a warning; recording a result later owns the league-rule validation.

## Minimal storage

Each record needs only:

| Field | Meaning |
| --- | --- |
| `league_id` | Existing league association/foreign key |
| `id` | UUID generated by the frontend and retained through edits/retries |
| `value` | One text column containing the complete planned matchup |

Use a unique key on `(league_id, id)`. No additional server-generated ID, format,
participant columns, scores, timestamps, or player/pair foreign keys are required.
Store `value` exactly as received after validation. Do not lowercase, trim, or
reorder the stored string. Frontend code parses it for display.

## Value grammar

```text
Singles: player1 player2
Doubles: player1,player2 player3,player4
```

There is exactly one ASCII space (U+0020) between opposing sides. A comma joins the
two teammates on a doubles side. Each nickname is nonempty and contains no comma
or whitespace. Both sides must have the same size: one or two. Preserve case,
Unicode characters, and nickname order. No escaping/quoting syntax is supported.
Repeated nicknames/matchups are allowed at the planning layer.

Valid values: `Alice Bob`, `민수 지수`, `Alice,Bob Charlie,Diana`, `A-1,B_2 C.3,D4`.

Invalid values: empty string, `Alice`, ` Alice Bob`, `Alice Bob `, `Alice  Bob`,
`Alice,Bob Charlie`, `Alice Bob,Charlie`, `Alice, Bob,Charlie`,
`Alice,,Bob Charlie,Diana`, `Alice\tBob` (a literal tab), or a newline/NBSP in a name.

Perform only this lightweight grammar validation; do not add participant lookups
or domain match validation. The frontend implementation is in `js/plan/model.js`.

## Batch upload

`POST /leagues/{league_id}/planned-matches`

Headers: `Content-Type: application/json`. No `X-Host-Token` required.

```json
{
  "matches": [
    {"id": "d315f636-10e5-4265-9b19-fc260e1ed224", "value": "Alice Bob"},
    {"id": "719e28b2-bce7-4e48-92a7-204711504dc8", "value": "Alice,Bob Charlie,Diana"}
  ]
}
```

Validate a nonempty `matches` array, UUID IDs, string values, and the value grammar.
Reject duplicate IDs within the same request as invalid input. Reject unexpected
item fields. Apply the entire batch in one database transaction: either every item
is saved or none are. Upsert on `(league_id, id)`:

- New IDs add plans without replacing the existing shared list.
- Existing IDs replace only that plan's `value`.
- Retrying an identical batch creates no duplicates.
- Plans omitted from a batch are untouched.

Return HTTP **200** with the accepted records, in request order:

```json
{
  "matches": [
    {"id": "d315f636-10e5-4265-9b19-fc260e1ed224", "value": "Alice Bob"},
    {"id": "719e28b2-bce7-4e48-92a7-204711504dc8", "value": "Alice,Bob Charlie,Diana"}
  ]
}
```

## Read shared plans

`GET /leagues/{league_id}/planned-matches`

Return HTTP **200**, `{ "matches": [{ "id": "...", "value": "..." }] }`, using
the same record shape. Return `{ "matches": [] }` for a league with no plans.
Return all records for this first version, in ascending UUID order for deterministic
responses; no timestamp/order column is required. No pagination, filters, or extra
metadata are requested. Local draft display keeps its own insertion order.

## Errors

Use the backend's normal error envelope and existing framework validation conventions:

- **422** for invalid UUIDs, request shape, duplicate request IDs, or invalid values.
- **404** when the league does not exist.
- **5xx** for unexpected storage errors, with the transaction rolled back.

The frontend must be able to rely on the status code without parsing a particular
error message. Do not return success for partial batches. Do not add authentication
requirements beyond the league link.

## Shared player nickname rule

Check whether Backend Main already enforces this rule. If not, add it to the shared
player nickname/alias validator used by registration, initial league players,
renaming, alias creation, and match submissions:

1. Trim surrounding whitespace using the existing nickname normalization convention.
2. Require a nonempty result containing neither whitespace nor a comma.
3. Preserve internal characters; never strip invalid characters to make a name valid.

The frontend uses JavaScript `/[\s,]/u` after `.trim()` in `js/nicknames.js`.
For cross-language consistency, whitespace means U+0009–000D, U+0020, U+00A0,
U+1680, U+2000–200A, U+2028, U+2029, U+202F, U+205F, U+3000, and U+FEFF.
Retain any stricter pre-existing nickname constraints. Examples for both sides:

| Nickname input | Expected |
| --- | --- |
| `Alice`, `민수`, `A-1`, `B_2`, `C.3` | Valid |
| `  Alice  ` | Valid after trimming to `Alice` |
| Empty or whitespace-only | Invalid |
| `Alice Smith`, `Alice,Bob` | Invalid |
| `Alice\tBob`, `Alice\nBob`, `Alice\u00a0Bob` (actual characters) | Invalid |

Bulk player inputs can use comma/newline delimiters, then validate each name.
This list-entry convention is not an exception allowing commas inside a nickname.
Do not silently rename/migrate existing players. Existing records remain readable
and removable; old names used solely to identify a player being renamed must not
prevent correcting that player's name.

## Acceptance tests required in the backend implementation

1. Upload and read singles and doubles, including Korean and unknown nicknames.
2. Verify exact `id`/`value` round trips, without added participant or format fields.
3. Repeat a batch: no duplicates. Change one existing ID's value: update that row.
4. Upload additional IDs: existing unrelated plans remain.
5. Verify isolation across leagues, including the same ID in two leagues.
6. Invalid item in a mixed batch or a storage failure: no partial writes.
7. Validate UUIDs, duplicate request IDs, malformed values, and missing leagues.
8. Verify anonymous league-link access and empty-list behavior.
9. Confirm uploads do not create/change players, aliases, pairs, recorded matches,
   or standings, regardless of registration/pair/rematch settings.
10. Cover the nickname-rule examples on every affected player-write path, including
    aliases, initial registration, and preserving access to legacy records.

No server-side delete endpoint, scheduling fields, result-recording integration,
or server-plan UI is requested in this version.
